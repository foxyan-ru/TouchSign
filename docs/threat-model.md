# Threat model

Short version: TouchSign proves a specific FIDO2 hardware key was
physically touched at signing time. It is only as strong as (a) that key
never leaving the legitimate contributor's control, and (b) the assumption
that a human touching a key to sign is also the human who wrote the diff.
Neither assumption is airtight, and this document tries to be explicit
about where the edges are.

## Out of scope: stolen or coerced keys

If a contributor's FIDO2 authenticator is physically stolen, or the
contributor is coerced into touching it, TouchSign (and git's underlying
SSH-signing mechanism) cannot detect this. This is the same limitation any
hardware-key-based auth system has -- a hardware token proves possession,
not consent or rightful ownership. Mitigations here are entirely
organizational (report lost/stolen keys immediately so the contributor's
line can be revoked from `allowed_signers` via a PR, as described in
`internal/registry`) and outside what a repository-local tool can enforce.

Similarly, a contributor who deliberately shares their authenticator PIN
and hands the physical key to someone else (say, to have a colleague "just
touch it for me") defeats the guarantee entirely, indistinguishably from a
legitimate self-touch. TouchSign has no way to observe this and doesn't try
to.

## What the anomaly detector catches, and what it doesn't

`internal/anomaly.DetectTimingAnomalies` flags pairs of commits from the
**same signer** whose signed timestamps are closer together than a human
could plausibly produce by physically touching a security key twice
(default floor: 300ms). This catches:

- A script that generates and signs many commits in a tight loop using a
  cached or replayed assertion.
- Bulk commit-timestamp manipulation (`git commit --date=...` or rebase
  scripts) that doesn't account for the physical touch requirement.
- Automation that expects to "sign like a human" without actually having a
  human present for each operation.

It does **not** catch:

- A single commit whose *content* was generated by an LLM and then signed
  normally by the actual human who touched the key. Signing cadence says
  nothing about authorship of the diff -- see the README's "What this does
  NOT prove" section. This is a fundamental limitation of the entire
  approach, not a gap specific to this detector.
- Two different signers acting close together in time. That's expected and
  explicitly not flagged (see the anomaly package's own tests) -- two
  different physical people can legitimately commit within the same
  second.
- A slow, patient automation that waits out the timing floor between
  signatures. The floor only defends against *implausibly fast* cadences;
  it cannot distinguish a deliberately-throttled script from a human once
  the gap between signatures is inside plausible human territory.
- Anything about the *quality*, correctness, or provenance of the code
  itself -- TouchSign has no opinion on diff content whatsoever.

## False positives and manual override

The most likely false positive is a legitimate rapid double-commit by the
same human: for example, `git commit --amend` followed immediately by
another commit, or a fast `git rebase --continue` loop where the
authenticator's touch requirement is satisfied by a single physical touch
that (depending on the OpenSSH/authenticator caching behavior) gets reused
across an unusually short window, or a contributor genuinely fast at
alternating between two prepared commits.

TouchSign treats every timing anomaly as a *signal for human review*, not
an automatic hard block, unless a specific policy rule sets
`block_on_anomaly: true` for a matched path (see `internal/policy` and
`docs/policy-example.yaml`). For paths where anomalies are reported but not
blocking, a reviewer who recognizes a false positive (e.g. "yes, that was
me amending twice in a row") can simply approve the PR as normal --
TouchSign's policy evaluation is a check, not a merge gate enforced outside
normal branch-protection review, so the standard "an authorized reviewer
can override a failing check" mechanism your forge already provides
(e.g. GitHub's "Merge without waiting for requirements" for repository
admins) is the intended manual-override path. TouchSign does not implement
its own separate override/approval flow -- deliberately, to avoid
duplicating access control git hosting already provides.

For repositories that want a *lower-friction* default, tuning
`min-gap-ms` down (or setting `block_on_anomaly: false` more broadly) is
the expected knob; the 300ms default in
`anomaly.DefaultMinPlausibleGapMs` is intentionally conservative in favor
of fewer false positives, not maximum sensitivity.
